# Research: Always-on agent harness (OpenClaw / Hermes) vs. custom bot for Coach's runtime

> Ticket: [#12](https://github.com/msinghbehl/AI_PM_Learning_Bot/issues/12)
> Date: 2026-07-25
> Status: Resolved — recommendation: **stay custom for Phase 1; revisit harness adoption as a Phase 2+ question.**

---

## 1. What OpenClaw and Hermes are

Both are **open-source (MIT), self-hosted, always-on personal agent harnesses** released in late 2025 / early 2026. They are the two most-starred projects in this category as of mid-2026.

| | OpenClaw | Hermes Agent |
|---|---|---|
| Steward | OpenClaw Foundation (community; OpenAI sponsor) | Nous Research |
| Core language | TypeScript | Python |
| GitHub stars (Jun 2026) | ~383k | ~217k |
| The bet | **Presence** — one event loop; messages, heartbeats, crons, webhooks feed one conversation; unbounded memory; "feels like a person" | **Discipline** — separated execution domains; sandboxed cron; bounded (~3k-char) user model; script-gated wake-ups; "feels like a harness" |
| Proactivity | Native HEARTBEAT — background events inject into the main conversation | No heartbeat; cron runs are isolated; `wakeAgent` script gate decides whether to wake the LLM |
| Memory | Accumulates unbounded memory of the user | Layered memory, deliberately bounded; FTS5 cross-session recall + Honcho dialectic user modeling |
| Skills | 13,700+ community skills (ClawHub marketplace) | Skills are mostly **self-generated by the learning loop**; agentskills.io standard |
| Channels | Dozens (WhatsApp, Discord, Slack, Teams, etc.) | 20+ platforms from one gateway (Telegram, Discord, Slack, WhatsApp, Signal, Matrix, ...) |
| Security posture | Relaxed by default ("free reign"; users sandbox themselves) | Restrictive by default (permission prompts, confined scripts, per-domain isolation) |
| Config surface | Fully drivable from chat | Several commands are CLI/TUI-only — hard to administer from Telegram alone |
| Release tempo | ~82 releases; fast-moving, frequently breaking | ~6 releases; conservative |
| Cron / scheduling | Native | Native (built-in cron with delivery to any platform) |
| Self-improvement | Skills marketplace (community-authored) | **Closed learning loop** — creates skills from experience, improves them during use, nudges itself to persist knowledge |

**Sources:** [The New Stack — OpenClaw and Hermes agree on what an agent is](https://thenewstack.io/openclaw-hermes-agent-harness/), [best-of-Agent-Harnesses comparison](https://github.com/RyanAlberts/best-of-Agent-Harnesses/blob/main/comparisons/openclaw-vs-hermes.md), [Hermes Agent docs](https://hermes-agent.nousresearch.com/docs/).

## 3. The trade-off

### What a harness *gives* Coach that the custom bot doesn't

- **Always-on runtime for free** — no Mac-awake skip risk; both can run on a $5 VPS or serverless (Hermes has Daytona/Modal backends that hibernate when idle). This is the one real Phase-1 gap in the custom design (#9's skip-if-asleep).
- **Channel breadth** — if Coach later wants to deliver on Discord/Slack/email, a harness has that built in. Custom bot is Telegram-only.
- **Hermes's self-improving skills loop** — superficially matches Coach's "self-improving" principle (PLAN §2.4). But Coach's self-improvement is *curriculum* self-improvement (SR re-asks, source ingestion), not *agent skill* self-improvement. They are different loops.
- **Memory across sessions** — Hermes's layered memory could, in principle, replace some of the SQLite state. But Coach's state is structured (SR intervals, mastery scores, cost ledger) — not the kind of unstructured conversational memory these harnesses optimize for.

### What a harness *costs* Coach

- **It replaces the substrate, not just the runtime.** The five ported Task_IQ patterns (#4) — JobQueue, allowlist, config enums, reflexive reprompt, tenacity retry — become harness configuration instead of ported code. The porting work isn't saved; it's *transformed* into learning a harness's config surface. For OpenClaw (TypeScript), the port is a language switch; for Hermes (Python), it's a framework switch.
- **The custom logic is still custom.** SM-2 SR, rubric grading, the cost-ledger fallback ladder, the PR-staging + human-review gate — none of these exist in either harness. They'd be built as harness skills/tools/plugins, which is *more* indirection than building them directly in a custom bot.
- **Operational weight.** Field reports (best-of-Agent-Harnesses) flag OpenClaw's release churn (82 releases, frequent breakage) and Hermes's CLI-only admin (hard to drive from Telegram alone — and Telegram is Coach's *only* channel in Phase 1). Either harness is heavier to operate than a single Python process.
- **Cost surprise risk.** The same field reports document the April–June 2026 billing earthquake: always-on agents on frontier models ran $0.50/hr ($360/mo) before optimization. Coach's cost design (#5) is deliberately ~$3/mo; a harness's heartbeat/cron defaults could blow that budget silently if not carefully gated. The custom bot's JobQueue fires *two* jobs/day; a harness's event loop may wake the model far more often.
- **It over-answers the Phase 1 question.** Phase 1 is a 2-week validation of the *pedagogy loop* (#8), not a production always-on system. A harness is the answer to "how do I run an agent 24/7 reliably" — which is a Phase 2+ question (#9 explicitly deferred always-on hosting to Phase 2).

### The design-philosophy mismatch

Coach is **opinionated about its own loop**: the pedagogy model (#2), the grading trust floor (#6), the curriculum schema (#7), the cost ladder (#5), and the human-review gate on every artifact (#3) are all *load-bearing custom logic*. A harness is a general-purpose runtime that optimizes for *breadth of capability* (OpenClaw) or *unstructured memory depth* (Hermes). Coach doesn't want breadth or unstructured memory — it wants a tightly-controlled teaching loop with structured state. Adopting a harness means fitting an opinionated custom loop *inside* a general-purpose runtime, which is more indirection than building the loop directly.

Hermes's "self-improving skills" loop is the closest fit to Coach's spirit, but it improves *the agent's skills* (procedural memory for doing tasks), not *the user's mastery* (SR intervals on curriculum concepts). They sound similar; they are different systems. Coach's self-improvement is a curriculum/SR loop, not an agent-skill loop.

## 4. Does a harness change any decided ticket?

| Decided ticket | Changed by a harness? |
|---|---|
| #2 Pedagogy | No — pedagogy is channel- and runtime-agnostic. |
| #3 Delivery surface (hybrid: Telegram + repo) | Partially — a harness could deliver to multiple channels and its memory could hold lessons, but the PR-staging + human-review gate is still custom. No decision reversed. |
| #4 Reuse boundary (port 5 patterns) | **Yes** — the ported patterns become harness config, not ported code. This is the one ticket a harness materially changes. |
| #5 Model routing (Anthropic direct, Haiku/Sonnet) | No — both harnesses are model-agnostic; the `call_llm` wrapper decision holds. |
| #7 Curriculum source | No — curriculum is independent of runtime. |
| #9 Hosting (JobQueue, Mac-awake, skip-if-asleep) | **Yes** — a harness removes the skip-if-asleep limitation and changes the hosting story from "Mac-awake" to "always-on VPS/serverless." |

So a harness touches 2 of 6 decided tickets (#4, #9) — the runtime substrate, not the pedagogy/grading/curriculum/delivery decisions. That means the harness question is *orthogonal* to most of the map: it's a runtime choice, not a product choice.

## 5. Recommendation

### Stay custom for Phase 1. Revisit harness adoption as a Phase 2+ question.

**Rationale:**

1. **Phase 1 is pedagogy validation, not infrastructure validation.** The 2-week exit criterion (#8) tests whether the daily loop + SR + grading works for Manmeet. A custom bot tests exactly that. A harness tests "can I operate OpenClaw/Hermes" *in addition* to the pedagogy — adding a confounder to a validation that should be clean.

2. **The custom logic is still custom.** SM-2, rubric grading, the cost ladder, and the PR-staging gate don't exist in either harness. Building them as harness skills/plugins is *more* work than building them in a custom bot, because of the indirection layer.

3. **The one real harness advantage (always-on) is a Phase 2 concern.** #9 already deferred always-on hosting to Phase 2. The Mac-awake skip-if-asleep model is an accepted Phase 1 trade-off, not a problem to solve now.

4. **Cost control is tighter in the custom bot.** Coach's $3/mo target (#5) depends on *two* model calls/day (7am generate, 11pm grade) plus on-demand answers. A harness's event loop, heartbeat, or cron defaults could silently multiply calls. The custom bot's JobQueue is the minimal-cost scheduling primitive.

5. **The ported patterns (#4) are already decided and cheap.** Five small patterns, proven in Task_IQ, ported into a clean repo. Replacing them with harness config is a net-zero swap that adds learning-curve risk.

6. **Hermes's self-improving loop is a different loop.** It improves agent skills, not user mastery. Coach's self-improvement (SR re-asks, curriculum ingestion) is custom either way.

### When to revisit (Phase 2+ triggers)

- **If Coach outgrows Telegram** — multi-channel delivery (Discord, email, SMS) is the harness's strongest case. If Phase 2 wants channel breadth, reassess.
- **If always-on becomes a real requirement** — when the Mac-awake skip becomes intolerable (e.g. missed pushes during travel), a harness on a $5 VPS is cleaner than custom cron + hosting.
- **If the source-fetcher + curriculum-ingestion loop (Phase 2, PLAN §4.5) wants agent autonomy** — Hermes's self-generated skills for "fetch, summarize, propose curriculum node" could fit the integrator role. This is the one place a harness's self-improvement loop *might* align with Coach's.
- **If Coach wants to become a general-purpose personal agent** beyond learning — then a harness is the right substrate. But that's a different product.

### If forced to pick a harness today: Hermes (Python, not OpenClaw)

- Python matches Coach's stack and Task_IQ's ported patterns (#4).
- Restrictive-by-default security aligns with Coach's human-review-gate philosophy (#3).
- Conservative release tempo (6 vs 82) is safer for a personal project.
- The `wakeAgent` script gate aligns with Coach's cost-control design (#5) — wake the LLM only when a deterministic check says it's worth it.
- But: Hermes's CLI-only admin is a real friction for a Telegram-only Phase 1, and its self-improving-skills loop doesn't map to Coach's SR loop.

## 6. What this does NOT change

- No decided ticket (#2, #3, #4, #5, #7, #9) is reversed.
- The custom bot + JobQueue + SQLite architecture (#9) stands for Phase 1.
- The ported patterns (#4) stand.
- The map's destination (decision-complete plan for Phase 1 build) is unaffected — the runtime substrate was already decided in #9; this research confirms that decision holds.
